# agentic-analyst

Агент-аналитик над реальными e-commerce данными: отвечает на вопросы, требующие
одновременно **чисел из базы** и **контекста из документов**.

> «Почему в категории *furniture_decor* выросла доля возвратов в Q3 2018?»
>
> Чтобы ответить, агент обязан сходить в SQL за динамикой, найти в регламентах
> действовавшие тогда правила возврата и доставки, и связать одно с другим.

Проект не про «сделал RAG». Он про то, **какой ценой** достигается качество:
каждое архитектурное решение здесь измерено и сведено в таблицу компромиссов.

---

## Результаты

Главный артефакт репозитория. Все числа получены на синтезированном golden set
(`evals/golden_set.jsonl`), прогон воспроизводится командой `make eval`.

### Retrieval

Два набора вопросов: **лёгкий** — сформулированы лексикой документа,
**трудный** — теми же словами, какими спросил бы пользователь. Разрыв между
ними и есть цена лексического несовпадения. Все решения оцениваем по трудному.

| Конфигурация | recall@5 лёгкий | recall@5 трудный | recall@1 трудный | MRR трудный | p50 реранка |
|---|---|---|---|---|---|
| Dense, bge-m3, чанк 400/60 | 0.879 | 0.765 | 0.510 | 0.623 | — |
| + реранкер, окно 20 | 0.956 | 0.882 | 0.471 | 0.657 | 2.8 с |
| **+ название документа в чанке** | 0.956 | 0.863 | **0.765** | **0.820** | — |
| + название + реранкер, окно 20 | 0.989 | 0.941 | 0.667 | 0.787 | 2.5 с |
| + название + реранкер, окно 50 | 0.989 | **0.961** | 0.667 | 0.791 | 4.6 с |
| + название + раздел + шапка таблицы | 0.943 | 0.843 | 0.647 | 0.755 | — |
| + BM25 (гибрид, RRF) | снято: на трудном наборе не за что зацепиться (решение №12) | | | | |
| ANN (HNSW) вместо точного поиска | — | — | — | — | — |

**Лучшей строки в этой таблице нет — есть лучшая под задачу.** Если топ-5 уходит в
контекст модели, побеждает связка с реранкером: 0.961. Если показываем один ответ или
агент берёт один документ, реранкер надо **выключить**: он роняет recall@1 с 0.765 до
0.667. Разбор причины — решения №11 и №13.

Реранкер: `bge-reranker-v2-m3`, float16, Apple M4 GPU. Латентность — медиана по
одиночным запросам, не батчем: в проде запрос приходит один.

**Читать эту таблицу надо по колонкам, а не по одной цифре.** recall@5 на трудном
наборе вырос на 0.137, но recall@1 при этом **упал** — реранкер лучше собирает
верную пятёрку и хуже выбирает единственный лучший. Разбор причины — решение №11.

## Архитектура

```
Вопрос
  │
  ├─ переписывание запроса (свёртка истории диалога)
  │
  ▼
Агент (tool calling, цикл с лимитом итераций)
  │
  ├──► sql_query      DuckDB: агрегаты, динамика, срезы
  ├──► search_docs    гибридный поиск + реранкер по регламентам
  └──► calculator     арифметика, которую LLM делает ненадёжно
  │
  ▼
Ответ + ссылки на источники
  │
  └─ трейс в Langfuse: шаги, tool calls, вход/выход каждого шага,
     латентность и токены по шагам
```

**Почему два разных инструмента, а не один.** Выбор инструмента становится
нетривиальным решением модели, а не заранее прописанной веткой — появляется
настоящий agent flow, который есть что оптимизировать. Плюс инструменты
отличаются по стоимости на порядки (SQL — миллисекунды, поиск — сотни мс,
шаг LLM — секунды), что даёт реальную поверхность для работы с латентностью.

## Стек

Ни одного сервера: всё поднимается из pip и работает локально.

| Слой | Выбор | Почему |
|---|---|---|
| Данные и SQL | **DuckDB** | Читает CSV напрямую, полноценные оконные функции |
| Эмбеддинги | **bge-m3**, локально | Мультиязычная, ~2 ГБ, CPU. Нулевая стоимость и нет rate limit |
| Лексический поиск | **DuckDB FTS** (BM25) | Гибрид без отдельного сервиса |
| Реранкер | **bge-reranker-v2-m3**, локально | Cross-encoder, применяется к top-50 |
| Векторный поиск | numpy exact → Qdrant HNSW | Точный поиск как эталон, ANN как измеренный компромисс |
| LLM | Groq / Mistral / Gemini | Swappable, free tier, замеры по трём провайдерам |
| Трейсинг | **Langfuse** | Шаги агента, tool calls, латентность и стоимость |

**Кеш вызовов LLM** (`src/llm/cache.py`) — обязательная часть, а не оптимизация:
прогон ablation это больше тысячи запросов, на free tier в лимиты не влезть,
а повторные прогоны обязаны быть воспроизводимыми и бесплатными.

**Судья для evals всегда другая модель, чем генератор** — иначе модель
систематически завышает оценку собственным ответам. Это проверяется на старте
и падает с ошибкой, если провайдеры совпали.

## Как измеряется качество

Размеченных данных нет, поэтому golden set **синтезируется**: по случайному
чанку модель генерирует вопрос, ответ на который в этом чанке содержится, —
получаются пары «вопрос → эталонный фрагмент». Часть просматривается руками,
мусор отбрасывается. Отдельно добавлены сложные типы:

- вопросы, требующие двух источников сразу (SQL + документ);
- вопросы, ответа на которые в корпусе нет (проверка, что агент говорит «не знаю»);
- вопросы с опечатками и на другом языке.

**Retrieval:** recall@k, MRR, NDCG по эталонным фрагментам.
**Генерация:** faithfulness (доля утверждений ответа, выводимых из контекста),
answer relevancy, context precision — reference-free, эталонный ответ не нужен.
**Агент:** task success rate, точность выбора инструмента, число шагов, стоимость.

Судья валидируется на человеческой разметке: 100 примеров размечены вручную,
считается согласованность. Без этого шага судья — просто ещё одна непроверенная
модель.
